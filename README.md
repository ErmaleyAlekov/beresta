# Берёста

**Русский** · [English](README.en.md)

**Берёста** (`beresta`) — XML-библиотека на **C++17** без единой сторонней зависимости. Она полностью заменяет Xerces-C++: DOM, SAX, пространства имён, кодировки, DTD, XML Schema, XPath 1.0, XInclude, обход дерева и сериализация.

Ядро собирается в динамическую библиотеку с плоским Си-интерфейсом. Поэтому «Берёстой» можно пользоваться не только из C++, но и из **C**, **Java 22+** (Project Panama, без JNI), **C#** (P/Invoke), **Python** (ctypes) и **Node.js** (Node-API, без node-gyp, с типами TypeScript), а сборка в **WebAssembly** работает в браузере, Web Workers и Cloudflare Workers. Готовые обёртки лежат в `bindings/`, а пакеты для npm, PyPI и NuGet со всеми платформами собирает CI (см. [Готовые пакеты и релизы](#готовые-пакеты-и-релизы)).

Название — от берестяных грамот: на бересте на Руси писали документы. Библиотека тоже работает с документами, только с XML.

```cpp
#include "beresta.hpp"

beresta::Document doc = beresta::XmlParser().parse("<greeting lang=\"ru\">Привет</greeting>");
std::cout << doc.getRoot()->getTextContent();                    // Привет
std::cout << beresta::xpath::evaluateString(doc, "/*/@lang");     // ru
std::cout << doc.toString();                                      // <greeting lang="ru">Привет</greeting>
```

## Преимущества

### Коротко
1. **Полный набор стандартов без зависимостей.** XML 1.0, пространства имён, восемь кодировок, DTD, XML Schema 1.0 с ключами, весь XPath 1.0, XInclude, SAX, DOM Traversal — и ни одной сторонней библиотеки, даже iconv или ICU.
2. **Самое компактное дерево среди полноценных библиотек.** Каталог на 26 МБ занимает в памяти 172 МБ — против 248 МБ у libxml2 и 348 МБ у Xerces-C++ (см. [Производительность](#производительность)).
3. **Скорость полноценной библиотеки.** Разбор вдвое быстрее Xerces-C++, на тексте — почти наравне с libxml2. XPath быстрее libxml2, проверка по XSD в 1,8 раза быстрее Xerces-C++ — прямо во время разбора или потоком без дерева.
4. **Автономные узлы.** Узел создаётся без документа, переносится между документами без `importNode`/`adoptNode` и переживает документ, из которого его забрали. В C++ такого почти нигде нет (см. [сравнение](#сравнение-с-другими-библиотеками)).
5. **Безопасность по умолчанию.** Сущностные бомбы ограничены всегда, внешние ресурсы не загружаются без явного разрешения, регулярные выражения XSD работают за линейное время, а хеш-таблицы с ключами из документа защищены секретным ключом от атак через коллизии (hash flooding).
6. **Никакой рекурсии.** Разбор, копирование, сравнение, вывод, проверка по XSD и деструктор обходят дерево по явному стеку — глубокий документ не уронит процесс.
7. **Проверенность.** 159 модульных тестов, включая нагрузочные (20 потоков на общих дескрипторах, 50 000 переносов узлов, 50 000 атрибутов в теге, рекурсивная схема глубиной 10 000), 100 % применимых случаев W3C XML Conformance Test Suite, санитайзеры ASan/UBSan/LSan/TSan, фаззинг libFuzzer.
8. **Шесть языков из одного бинарника и WebAssembly.** C++, C, Java (Panama), C# (P/Invoke), Python (ctypes) и Node.js (Node-API) — всё в комплекте, без JNI, node-gyp и пакетов из сети. Тот же API для браузера и Cloudflare Workers — пакет `beresta-wasm`.
9. **Обёртки, которые не тормозят на тяжёлой работе.** Разбор, XPath и проверка по схеме идут внутри ядра со скоростью C++. Потоковая проверка из Java, .NET и Python быстрее родных средств этих языков, а гигабайтная выгрузка проверяется в десятках мегабайт памяти. Разбор с проверкой XSD в .NET в 2,3 раза быстрее `XmlDocument`, XPath в Java в 1,4–1,8 раза быстрее JDK (см. [Производительность](#производительность)).
10. **Готовые пакеты для всех платформ.** `npm install beresta`, `pip install beresta`, `dotnet add package Beresta`: внутри уже лежат бинарники для Windows и Linux (x64, arm64) и универсальный для macOS (Intel и Apple Silicon) — компилировать ничего не нужно.
11. **Сообщения на русском и английском.** Язык выбирается при сборке и меняется во время работы, новый язык добавляется одним файлом.
12. **Читаемый код.** Короткие функции, маленькие файлы, двуязычные комментарии везде — библиотеку можно прочитать, проверить и доработать самостоятельно.

### Современный C++
- **Только `std::string` в UTF-8.** Нет `XMLCh`, `XMLString::transcode()` и ручного `release()`. Значения из дерева сразу подходят любому коду на C++.
- **RAII везде.** Родитель владеет детьми через `std::unique_ptr`, поэтому `delete`, `release()` и `XMLPlatformUtils::Initialize/Terminate` не нужны, а утечки невозможны по построению.
- **Узлы автономны.** Глобального менеджера документа нет. Узел создаётся обычным конструктором, живёт где угодно и переносится в любое дерево без `importNode`/`adoptNode`. Пространство имён узла вычисляется по его текущему месту в дереве, поэтому после переноса оно всегда верное для нового документа.
- **Глубокое копирование одной строкой:** `Element copy = original;`. Для копирования через базовый класс есть виртуальный `clone()`.
- **Типизированные настройки.** Вместо строковых «фич» `DOMConfiguration` — обычная структура `ParserOptions`, и опечатку в имени ловит компилятор.
- **Строгие гарантии исключений.** Если вставка, замена или присваивание не удались, дерево остаётся прежним, а переданный узел остаётся у вызывающего.

### Разбор
- **Один парсер — два режима.** SAX-ядро генерирует события, DOM строится одним из обработчиков (паттерн Builder). SAX так же строг, как DOM.
- **Формат ввода не важен.** Отформатированный и «сплошной» XML дают одно и то же дерево.
- **Разбор на `std::string_view`.** Для UTF-8 входной текст не копируется: сканер возвращает срезы исходной строки.
- **Итеративный разбор без рекурсии.** Открытые элементы и тексты сущностей хранятся в явных стеках, поэтому глубокий ввод не переполнит стек вызовов.
- **Нигде нет рекурсии по дереву.** Копирование, сравнение, сериализация (обычная и с отступами), сбор текста, `normalize`, проверка по XSD и даже деструктор обходят дерево по явному стеку. Деструктор разбирает дерево вовсе без выделения памяти. Глубина документа ограничена только памятью: тесты строят, копируют, сравнивают, выводят и разбирают дерево глубиной 100 000 уровней.
- **Позиции ошибок в символах UTF-8.** Координаты считаются инкрементально и только по запросу. Позицию любого узла можно запомнить (`trackLocations`).

### Полный набор стандартов
- **XML 1.0 (5-я редакция):** проходит **100 %** применимых случаев официального W3C XML Conformance Test Suite (2001 из 2585; остальные — XML 1.1 и случаи для редакций 1–4), см. [`tests/conformance`](tests/conformance/README.md). Символы имён — по таблицам 5-й редакции.
- **Namespaces in XML:** проверка при разборе и «живые» URI в DOM.
- **Восемь кодировок:** UTF-8, UTF-16 LE/BE, ISO-8859-1, US-ASCII, windows-1251, windows-1252, KOI8-R, IBM866. Кодировка определяется по BOM и декларации. Все таблицы написаны самостоятельно, без iconv и ICU.
- **DTD:** внутреннее и внешнее подмножества, параметрические сущности, условные секции, атрибуты по умолчанию, полная проверка валидности, `getElementById`.
- **XML Schema 1.0:** 45 встроенных типов, фасеты, `restriction`/`extension`, `list`/`union`, `sequence`/`choice`/`all`, группы, `xs:any`, группы замены, `xsi:type` с проверкой наследования, `block`/`final`, абстрактные элементы и типы, `xsi:nil`, ID/IDREF, ограничения идентичности `xs:key`/`xs:unique`/`xs:keyref`, `include`/`import`/`redefine`/`override`.
- **XPath 1.0 целиком:** все 13 осей, включая `namespace`, все 27 функций базовой библиотеки, переменные и префиксы.
- **XInclude 1.0:** `parse="xml|text"`, `xi:fallback`, XPointer `element()` и по ID, защита от циклов.
- **DOM Traversal:** `TreeWalker` и `NodeIterator` с фильтрами — алгоритмы строго по спецификации W3C.

### Надёжность и безопасность
- **Защита от «billion laughs».** Лимиты на число, объём и вложенность раскрытий сущностей включены всегда, а не отдельной настройкой.
- **Нет XXE и SSRF по умолчанию.** Без явного `ResourceResolver` ничего внешнего не загружается. `FileResourceResolver` не выходит за корневой каталог и отвергает сетевые URI.
- **Защита от hash flooding.** Хеш-таблицы, ключи которых приходят из документа (значения ID, имена элементов и атрибутов), используют SipHash-1-3 со случайным ключом процесса: заранее подобрать строки с одинаковым хешем нельзя.
- **Нет квадратичных проверок на враждебном вводе.** Повторы атрибутов ищутся перебором только у тегов с несколькими атрибутами, дальше — хеш-таблицей. Тег со 100 000 атрибутов (1,3 МБ) разбирается за 0,07 с.
- **Своё регулярное выражение XSD на НКА Томпсона.** Время проверки линейно, «катастрофический бэктрекинг» невозможен в принципе.
- **Точная арифметика фасетов.** Десятичные числа сравниваются как строки цифр любой длины, без потери точности на `double`.
- **Проверено санитайзерами:** все тесты проходят под AddressSanitizer, LeakSanitizer, UBSan и `_GLIBCXX_ASSERTIONS` — без утечек памяти, неопределённого поведения и выхода за границы контейнеров, а под ThreadSanitizer — без гонок (20 потоков на общих схеме, XPath и документе).
- **Нагрузочные тесты под сценарии обёрток:** 50 000 переносов узлов между документами с проверкой каждого ранее выданного дескриптора после освобождения исходного документа; время разбора тега с 50 000 и 200 000 атрибутов растёт линейно; рекурсивная схема глубиной 10 000 уровней проверяется одинаково в SAX, DOM и по готовому дереву.
- **Индекс ребёнка за O(1).** Узел хранит свой номер среди соседей, поэтому `nextSibling`, `removeChild` последнего ребёнка и перенос узлов из обёрток не ищут узел перебором: 150 000 переносов из Си-интерфейса занимают 13 мс.
- **Проверено фаззингом:** три цели libFuzzer (разбор с любыми `ParserOptions`, XPath, XML Schema) под ASan + UBSan; последний раунд — ни одной находки, см. [`tests/fuzz`](tests/fuzz/README.md).

### Вывод
- **Компактный по умолчанию.** Ни одного лишнего пробела, порядок атрибутов сохраняется, повторный разбор вывода даёт тот же текст.
- **Красивый вывод по запросу.** Отступы ставятся только там, где они не меняют данные: смешанное содержимое выводится дословно.
- **Любая выходная кодировка.** Декларация сама получает правильный `encoding`, BOM пишется при необходимости, а символы вне кодировки становятся `&#N;`.

### Один бинарник — шесть языков
- **Плоский Си-интерфейс** (`extern "C"`, 71 функция): стабильный ABI, имена без декорирования, объекты наружу — непрозрачные дескрипторы `void*`. Исключения C++ никогда не пересекают границу библиотеки.
- **Java 22+ через Project Panama** (Foreign Function & Memory API): ни строчки JNI, Java работает с нативной памятью напрямую. Бинарник едет внутри jar и сам извлекается под нужную ОС и архитектуру.
- **C# через P/Invoke** с `SafeHandle`: память освобождается детерминированно (`using`) и гарантированно (при финализации). Пакет NuGet со стандартной раскладкой `runtimes/<rid>/native`.
- **Python через ctypes:** ни одного пакета из PyPI и ни одного компилятора на машине пользователя.
- **Node.js через собственный аддон Node-API:** без `ffi-napi`, node-gyp и npm-зависимостей; готовый бинарник едет в пакете, типы TypeScript — в комплекте.
- **WebAssembly** (`bindings/wasm`, пакет `beresta-wasm`): то же ядро, собранное Emscripten, и тот же JS-слой, что у Node.js, — DOM, XPath и XSD в браузере, Web Workers и Cloudflare Workers. Модуль весит около 650 КБ (около 250 КБ в gzip).
- **Универсальный бинарник для macOS:** `make universal` склеивает сборки x86_64 и arm64 через `lipo`, CMake делает то же с `CMAKE_OSX_ARCHITECTURES="x86_64;arm64"`.
- **Тяжёлая работа — внутри ядра.** XPath (`selectValues` без объектов-узлов), проверка по схеме и потоковая проверка файлов любого размера вызываются из любого языка одним вызовом, и через границу языка проходит только результат.
- **Сборка сама раскладывает бинарник.** CMake и Makefile определяют ОС и архитектуру процессора и копируют библиотеку в ресурсы Maven-проекта, в `runtimes/<rid>/native` для .NET, в пакет Python и (аддоном) в пакет npm.
- **Наружу видны только функции Си-интерфейса** — ровно 71 символ. Классы C++ скрыты (`-fvisibility=hidden`, на Windows экспортируется только `BERESTA_API`). C++ runtime встроен в библиотеку, поэтому на чистой машине не нужны ни `libstdc++`, ни `vcruntime`. На Linux символы встроенной `libstdc++` тоже спрятаны (`--exclude-libs,ALL`): в процессе JVM или Python они не конфликтуют с системной `libstdc++`.

### Инженерные качества
- **Ноль зависимостей:** только стандартная библиотека C++17. Обёрткам тоже ничего не нужно, кроме JDK, .NET, Python или Node.js.
- **Кроссплатформенность:** Windows, Linux, macOS, WebAssembly. Компиляторы MSVC, MinGW, GCC, Clang, Emscripten. Есть CMake и Makefile с автозависимостями, а CI в GitHub Actions собирает и проверяет всё это на каждый push.
- **Тип узла без `dynamic_cast` в ядре:** тип определяется через `getType()`, приведение — `static_cast`. Только Си-интерфейс проверяет дескрипторы через `dynamic_cast`: текстовый узел вместо элемента даёт ошибку `INVALID_ARGUMENT`, а не неопределённое поведение.
- **Сообщения на двух языках:** все тексты ошибок — в каталоге сообщений, русский и английский в комплекте. Язык по умолчанию выбирается при сборке, во время работы его меняет одна функция, а новый язык добавляется одним файлом.
- **Читаемый код:** функции не длиннее 25 строк, в файле не больше 5 функций, подробные двуязычные комментарии (русский и английский), классические паттерны (Composite, Template Method, Builder, Facade, Strategy, Interpreter, Observer, Factory Method, Adapter).

| Обёртки в комплекте | C, Java, C#, Python, Node.js | нет (сторонние: lxml, libxmljs) | нет | нет | нет | нет |
| WebAssembly в комплекте | да, `beresta-wasm` | нет (сторонние сборки) | нет | нет | нет | нет |
| Защита хеш-таблиц от коллизий | SipHash со случайным ключом | да (случайное зерно словаря) | нет | хеш-таблиц для входа нет | хеш-таблиц для входа нет | хеш-таблиц для входа нет |
| Сторонние зависимости | нет | zlib, iconv, ICU (необязательно) | ICU, curl (необязательно) | нет | нет | нет |
| Лицензия | MIT | MIT | Apache 2.0 | MIT | zlib | Boost / MIT |

**Автономность узлов** в других библиотеках:
- **Xerces-C++** и все реализации W3C DOM (JAXP в Java, `XmlDocument` в .NET, DOM браузера) привязывают узел к документу-владельцу: создать его можно только через `document.createElement`, а в другой документ — только через `importNode` (копия) или `adoptNode`. Память узлов Xerces освобождается вместе с документом.
- **libxml2** позволяет создать узел без документа (`xmlNewNode(NULL, ...)`), но при переносе между документами надо самому исправлять ссылки на словарь строк документа и на объявления пространств имён (`xmlDOMWrapAdoptNode`, `xmlReconciliateNs`). Ошибка здесь — висячий указатель.
- **pugixml, tinyxml2, RapidXML** выделяют узлы из пула своего документа: узел не существует без документа, а перенести его в другой документ можно только копированием.
- Похожая модель есть в других языках: **LINQ to XML** (`XElement` в .NET), **JDOM** в Java и **ElementTree** в Python. В C++ «Берёста» даёт то же самое, но с владением через `std::unique_ptr`: кто держит указатель, тот и владеет узлом.

**Что выбрать.** Если нужен только быстрый разбор доверенного XML без пространств имён и проверок — pugixml или RapidXML быстрее в 10–15 раз. Если нужна строгая проверка самой схемы по всем ограничениям XSD 1.0 (корректность `restriction` для моделей содержимого, однозначность модели — UPA) — Xerces-C++. Большие отраслевые схемы с `xs:redefine` и группами замены «Берёста» загружает и проверяет сама. «Берёста» — для всего между ними: полноценный XML с пространствами имён, DTD, XSD и XPath, безопасный по умолчанию, без зависимостей, с удобным C++ API, обёртками для пяти языков и WebAssembly.

## Где применять

«Берёста» рассчитана на задачи, где XML — формат обмена со строгими правилами: документ обязан соответствовать схеме, проверку нельзя пропустить, а данные приходят извне и могут оказаться враждебными.

### Разработчикам в России и СНГ

Здесь XML — основной формат юридически значимого обмена, и почти всегда он описан схемами XSD. Несколько типичных задач:

- **Отчётность в ведомства.** Электронная отчётность в ФНС, СФР и другие органы передаётся в XML-форматах, которые публикуются вместе со схемами XSD. Файл можно проверить по схеме ещё до отправки: каждая ошибка приходит с путём к элементу (`/Файл/Документ/СвНП[1]`), позицией и понятным текстом на русском.
- **Межведомственное взаимодействие (СМЭВ 3).** Конверты SOAP и виды сведений описаны XSD с пространствами имён. Ключи и ссылки между записями (`xs:key`, `xs:keyref`, `xs:unique`) проверяет сама схема, без кода на стороне приложения.
- **Электронный документооборот.** УПД, счета-фактуры и акты в форматах ФНС, документы с кодами маркировки, обмен с ЕГАИС — это XML со строгими схемами и кириллицей. Восемь кодировок, включая windows-1251, KOI8-R и IBM866, работают без iconv и ICU.
- **Закупки и открытые данные.** Выгрузки ЕИС в сфере закупок и порталов открытых данных — большие XML-файлы. Для них есть потоковый SAX — в том числе с проверкой по XSD без построения дерева — и самое компактное дерево среди полноценных библиотек: в 1,4 раза меньше памяти, чем у libxml2, и вдвое меньше, чем у Xerces-C++.
- **Банки и финансы.** Платёжные сообщения ISO 20022 и электронные форматы Банка России — XML со схемами. Безопасность по умолчанию (нет XXE, сущностных бомб и атак через коллизии хешей) закрывает целый класс уязвимостей до того, как их найдёт аудит.
- **Учётные системы и торговля.** Обмен с 1С (EnterpriseData, CommerceML), маркетплейсами и интернет-магазинами идёт в XML. Одну и ту же схему можно проверять в сервисе на Java или .NET, в скрипте на Python, на сервере Node.js и прямо в браузере — с одинаковым результатом.
- **Закрытые контуры и импортозамещение.** Сторонних зависимостей нет, лицензия MIT, исходники открыты и читаемы (короткие функции, двуязычные комментарии): код можно проверить, собрать из исходников без доступа к интернету и включить в свой продукт. Ядро — переносимый C++17 без ассемблера и системно-зависимых расширений, поэтому должно собираться обычным GCC или Clang на отечественных дистрибутивах Linux. На Astra Linux, РЕД ОС, «Альт» и процессорах «Эльбрус» сборка в этом репозитории пока не проверялась.

### В любых проектах

- **Проверка XML в браузере и на edge.** `beresta-wasm` проверяет файл по XSD и выполняет XPath прямо на странице, ещё до отправки на сервер, а также в Web Workers.
- **Одинаковое поведение во всех языках.** Сервисы на Java, .NET, Python и Node.js используют одно ядро, поэтому одни и те же сообщения об ошибках, одни и те же правила пробелов и сравнения значений.
- **Интеграции SOAP и WSDL, конфигурации, RSS и Atom, SVG, XML внутри офисных форматов** (OOXML и ODF — это XML в архиве ZIP; распаковку делает приложение).
- **Встраиваемые системы и инструменты на C и C++.** Нет зависимостей и рекурсии, а расход памяти предсказуем: глубокий или огромный документ не уронит процесс.

Когда лучше взять другую библиотеку, сказано в разделе [Сравнение с другими библиотеками](#сравнение-с-другими-библиотеками) («Что выбрать»).

- **Разбор с проверкой по XSD** в 1,8 раза быстрее, чем у Xerces-C++, и в 1,2 раза медленнее, чем у libxml2. «Берёста» проверяет документ прямо во время разбора, одним проходом; libxml2 в этом замере строит дерево и проверяет его вторым проходом (`xmlSchemaValidateDoc`). Разрыв с libxml2 — в основном разница в скорости самого разбора (86 против 120 МБ/с): проверка «Берёсте» обходится не дороже.
- **Потоковая проверка без дерева** (`SaxParser` со схемой, а из обёрток — `validateFile`) — 93 МБ/с, в 1,5 раза быстрее, чем с построением дерева; у libxml2 (`xmlSchemaValidateStream`) — 112 МБ/с. Файл отображается в память, поэтому собственной памяти процессу нужно O(глубины документа): выгрузка на 135 МБ проверяется в 37 МБ, а в дерево ушло бы 857 МБ.

«Поток + XSD» у родных библиотек — их штатный способ проверить документ без DOM: `javax.xml.validation.Validator` над `StreamSource`, проверяющий `XmlReader`, прочитанный до конца, и `lxml.etree.iterparse` со схемой и очисткой элементов. Памяти потоковая проверка почти не требует: файл 135 МБ (500 000 товаров) через `schema.validate_file` из Python занимает на пике 37 МБ собственной памяти процесса, а через `parse_file` + `validate` — 857 МБ.

> 💡 **Как получить из обёртки скорость C++.** Медленное место любой обёртки — граница между языками. Каждый шаг ручного обхода (`firstChild`, `nextSibling`) — это вызов через Panama, P/Invoke или ctypes и новый объект-обёртка. Миллион мелких шагов из Python измеряют скорость ctypes, а не парсера. Поэтому тяжёлую работу отдавайте ядру целиком:
> - **XPath:** выражение (`XPath`) компилируется один раз и вычисляется сколько угодно раз, в том числе из разных потоков. Значения узлов берите через `selectValues` / `SelectValues` / `select_values`: строки собираются внутри ядра, и объекты-узлы не создаются.
> - **Проверка по XSD:** `schema.validate(document)` для готового дерева. В .NET это в 2,3 раза быстрее `XmlDocument` и в 1,5 раза быстрее `XDocument`.
> - **Потоковая проверка без дерева:** `validateFile` / `ValidateFile` / `validate_file`. Подходит для выгрузок в гигабайты: дерево не строится, а файл отображается в память.
>
> В этих сценариях «Берёста» работает со скоростью скомпилированного кода, а её дерево занимает примерно на 30 % меньше памяти, чем у JDK DOM и lxml.

Где обёртки имеют смысл:
- **Ядро везде одно и то же**, поэтому разбор и проверка по схеме идут со скоростью C++ (63–105 МБ/с) в любом языке. Пошаговый обход из обёртки всё равно в десятки раз медленнее, чем в родных библиотеках, хотя в Java он ускорен в 1,4 раза (`invokeExact` на горячих вызовах), а в Python — в 1,6 раза (тип узла и классы обёрток запоминаются).
- **Потоковая проверка по схеме** — выигрыш во всех трёх языках: быстрее `Validator` из JDK (97 против 90 МБ/с), быстрее проверяющего `XmlReader` из .NET (94 против 85) и почти вдвое быстрее lxml (93 против 49).
- **Node.js и браузер** — самый очевидный выигрыш: среди библиотек с настоящим DOM, XPath и XSD «Берёста» быстрее всех (см. таблицу выше), а встроенной проверки по XSD в браузере нет вовсе.
- **.NET** — разбор с проверкой по XSD в 2,3 раза быстрее `XmlDocument` (64 против 28 МБ/с) и в 1,5 раза быстрее `XDocument`, разбор на уровне `XDocument`. Если схема не нужна, `XDocument` быстрее и экономнее.
- **Java** — XPath в 1,4–1,8 раза быстрее, чем в JDK (по разным прогонам JDK показывает от 97 до 127 мс), дерево на 28 % компактнее (88 против 123 МБ), проверка по XSD наравне. Разбор медленнее встроенного Xerces-J. Важное отличие — безопасность по умолчанию: стандартный `DocumentBuilder` загружает внешние сущности (XXE), пока его явно не настроить.
- **Python** — lxml быстрее при разборе в дерево и в XPath, но потоковая проверка у «Берёсты» почти вдвое быстрее, а дерево на 28 % компактнее (86 против 119 МБ). XPath 1.0 и XSD работают без сторонних пакетов: встроенный `xml.etree` не умеет ни того, ни другого, а документация модуля `xml` прямо предупреждает о небезопасности на враждебных данных.
- **Общие причины выбрать обёртку:** одинаковые сообщения об ошибках (по-русски или по-английски), пути вида `/order/item[2]`, правила XPath и XSD во всех языках — микросервисы на Java, .NET, Python и Node.js проверяют одни и те же файлы одинаково. Защита от сущностных бомб и XXE включена в ядре, и её не нужно настраивать в каждом языке. Кодировки windows-1251, KOI8-R и IBM866 работают без внешних библиотек.

Повторить: `node benchmarks/wrappers/make_data.js`, затем программы в `benchmarks/wrappers/` — `WrapperBench` и `StreamBench` (Java), `WrapperBench` с ключом `--stream` (.NET), `bench.py` и `stream_bench.py` (Python); см. [`benchmarks/README.md`](benchmarks/README.md).

## Сборка и подключение

Нужен компилятор с поддержкой **C++17**. Есть два независимых способа сборки — CMake и Makefile; оба работают на Windows, Linux и macOS.

Что получается в результате:

| Файл | Для кого |
|---|---|
| `beresta.dll` / `libberesta.so` / `libberesta.dylib` | динамическая библиотека с Си-интерфейсом: C, Java, C#, Python |
| `libberesta.a` (Makefile) / `beresta_static` (CMake) | статическая библиотека для программ на C++ (полный C++ API) |
| `beresta.node` | аддон Node.js: переходники Node-API + ядро в одном файле |
| `beresta_core.wasm` + `beresta.mjs` | WebAssembly для браузеров, Workers и Node.js |

Из динамической библиотеки экспортируются **только** функции Си-интерфейса. Программы на C++ подключают статическую библиотеку.

| `make` / `make all` | `bin/libberesta.a`, динамическая библиотека, демо `bin/beresta_demo` (C++) и `bin/beresta_capi_demo` (C) |

| `make clean` | удаляет `obj/` и `dep/` |
| `make fclean` | `clean` + `bin/`, копии бинарника в обёртках, `bindings/wasm/dist/` и `bindings/java/target/` |
| `make re` | полная пересборка |

Особенности Makefile:
- `make -j` поддерживается, компилятор можно сменить (`make CXX=clang++ CC=clang`).
- Объектные и `.d`-файлы раскладываются по `obj/` и `dep/` зеркально `src/`. Изменённый заголовок пересобирает только зависимые файлы, а изменённый Makefile (например, флаги) — все объекты.
- Очистка сама определяет оболочку: `rmdir /S /Q` в `cmd.exe` на Windows и `rm -rf` в `sh` на Linux и macOS.
- Архитектура берётся у самого компилятора (`$(CXX) -dumpmachine`), поэтому при кросс-компиляции бинарник попадает в папку целевой платформы.
- Сборки для другой архитектуры и для WebAssembly идут отдельным запуском make со своими `obj/<arch>`, `dep/<arch>` и `bin/<arch>` и не смешиваются с обычной. На macOS код собирается для версии не ниже `MACOS_MIN` (по умолчанию 11.0 — первая с Apple Silicon).

По умолчанию CMake собирает **только ядро** — динамическую библиотеку:

### Куда копируется бинарник

CMake (модуль `cmake/BerestaPlatform.cmake`) и Makefile определяют **целевую** ОС и архитектуру и приводят имена к единому виду. Те же имена ищут загрузчики обёрток:

| Обёртка | Папка |
|---|---|
| Java | `bindings/java/src/main/resources/natives/<os>-<arch>/` |
| C# | `bindings/csharp/Beresta/runtimes/<rid>/native/` |
| Python | `bindings/python/beresta/_native/<os>-<arch>/` |
| Node.js | `bindings/node/native/<os>-<arch>/beresta.node` |

- `<os>-<arch>`: `windows-x86_64`, `windows-aarch64`, `linux-x86_64`, `linux-aarch64`, `macos-x86_64`, `macos-aarch64`, `*-x86`.
- `<rid>` (идентификатор среды .NET): `win-x64`, `win-arm64`, `linux-x64`, `linux-arm64`, `osx-x64`, `osx-arm64`.
- Источник архитектуры в CMake: `MSVC_CXX_ARCHITECTURE_ID` для MSVC (верно и для `-A ARM64`), `CMAKE_OSX_ARCHITECTURES` на macOS, иначе `CMAKE_SYSTEM_PROCESSOR`. Значения можно задать вручную: `-DBERESTA_PLATFORM_ARCH=aarch64`.
- Универсальный бинарник macOS (`make universal` или две архитектуры в `CMAKE_OSX_ARCHITECTURES`) кладётся сразу в папки `macos-x86_64` и `macos-aarch64` (`osx-x64` и `osx-arm64` для .NET): загрузчики находят его на любом Mac.
- Один jar, пакет NuGet, колесо Python или пакет npm для всех платформ собирает релизный CI: каждая ОС добавляет свою папку, а упаковка идёт один раз (см. [Готовые пакеты и релизы](#готовые-пакеты-и-релизы)).

## Быстрый старт

### Разобрать, найти, изменить, сохранить

```cpp
#include "beresta.hpp"
#include <iostream>

int main()
{
    try
    {
        beresta::Document doc = beresta::XmlParser().parseFile("library.xml");

        for (beresta::Element* book : beresta::xpath::selectElements(doc, "//book[@lang='ru']"))
            book->setAttribute("checked", "yes");

        beresta::SerializerOptions options;
        options.prettyPrint = true;
        beresta::XmlSerializer(options).writeFile(doc, "library.out.xml");
    }
    catch (const beresta::DomException& error)
    {
        std::cerr << error.what() << '\n';     // [PARSE_ERROR] строка 3, столбец 7: ...
        return 1;
    }
    return 0;
}
```

### Построить документ с нуля

```cpp
beresta::Document doc;
doc.setDeclaration(beresta::XmlDeclaration{"1.0", "UTF-8", std::nullopt});

beresta::Element* root = doc.setRoot(std::make_unique<beresta::Element>("note"));
root->setAttribute("title", "Q&A");
root->appendChild(std::make_unique<beresta::Comment>(" черновик "));

auto body = std::make_unique<beresta::Element>("body");
body->setTextContent("1 < 2");
root->appendChild(std::move(body));

std::cout << doc.toString();
// <?xml version="1.0" encoding="UTF-8"?><note title="Q&amp;A"><!-- черновик --><body>1 &lt; 2</body></note>
```

> Если в консоли Windows кириллица выводится «кракозябрами», переключите консоль в UTF-8: `SetConsoleOutputCP(CP_UTF8)` из `<windows.h>` (так сделано в `examples/` и `tests/`).

## Модель данных и память

### Иерархия классов (паттерн Composite)

```
Node                          абстрактный узел
├── ContainerNode             узел с детьми (абстрактный)
│   ├── Element               тег, атрибуты, дети
│   └── Document              декларация, DOCTYPE, пролог, один корень
├── CharacterNode             узел со строковым значением (абстрактный)
│   ├── Text
│   ├── Comment
│   └── CDataSection
├── ProcessingInstruction     <?target data?>
└── DocumentType              <!DOCTYPE ...> + модель DTD
```

`NodeType`: `DOCUMENT`, `DOCUMENT_TYPE`, `ELEMENT`, `TEXT`, `CDATA_SECTION`, `COMMENT`, `PROCESSING_INSTRUCTION`.

XML-декларация — не узел, а свойство документа (`Document::getDeclaration()`). Цель PI `xml` зарезервирована: `ProcessingInstruction("xml", ...)` бросает `INVALID_NAME`.

### Владение

- Родитель **владеет** детьми (`std::vector<std::unique_ptr<Node>>`).
- Ребёнок **знает** родителя через невладеющий указатель, а свой индекс среди соседей хранит сам. Поэтому `getNextSibling()` работает за O(1).
- Владение направлено только сверху вниз: циклов нет, и удаление корня освобождает всё поддерево.

**Почему не `shared_ptr` + `weak_ptr`:** тогда каждый узел пришлось бы создавать в `shared_ptr`, и обычное `Element copy = original;` на стеке не могло бы привязать детей к копии.

| Откуда указатель | Сколько он живёт |
|---|---|
| `appendChild`, `getChild`, `findChildElement`, `getRoot`, XPath, `TreeWalker` | пока узел в дереве и дерево живо |
| `removeChild`, `detachChild`, `replaceChild`, `releaseRoot`, `clone`, `parseElement` | вы владеете узлом (`unique_ptr`) |

## Работа с деревом

### Навигация

```cpp
beresta::Element* root = doc.getRoot();
beresta::Node* first = root->getFirstChild();
beresta::Node* next = first->getNextSibling();          // O(1)
beresta::Node* last = root->getLastChild();
std::size_t index = next->getIndexInParent();
beresta::Document* owner = next->getOwnerDocument();
bool inside = next->isDescendantOf(*root);
```

### Изменение

```cpp
root->appendChild(std::make_unique<beresta::Element>("item"));
root->insertChild(0, std::make_unique<beresta::Comment>("начало"));
std::unique_ptr<beresta::Node> old = root->replaceChild(1, std::make_unique<beresta::Text>("новое"));
std::unique_ptr<beresta::Node> taken = root->detachChild(*root->getLastChild());
root->normalize();                 // слить соседние Text, удалить пустые
root->setTextContent("только текст");
root->clearChildren();
```

### Атрибуты

```cpp
item.setAttribute("id", "42");                       // добавить или заменить (позиция сохраняется)
std::optional<std::string> id = item.getAttribute("id");
bool has = item.hasAttribute("id");
bool removed = item.removeAttribute("id");
for (const beresta::Attribute& a : item.getAttributes()) { /* a.name, a.value */ }
item.setAttributes({{"a", "1"}, {"b", "2"}});        // пакетом за O(n); имена проверяются до изменений
```

### Поиск

```cpp
const beresta::Element* first = root->findChildElement("item");                 // среди детей
std::vector<const beresta::Element*> direct = root->findChildElements("item");
std::vector<const beresta::Element*> deep = doc.getElementsByTagName("item");    // всё поддерево, "*" — любые
const beresta::Element* byId = doc.getElementById("b7");                         // ID из DTD или xml:id
```

Для сложных запросов используйте [XPath](#xpath-10).

### Сравнение и текст

```cpp
bool same = a.isEqualNode(b);               // структурное равенство; порядок атрибутов не важен
std::string text = element.getTextContent(); // текст потомков (Text и CDATA, без комментариев)
```

## Копирование и перенос узлов

```cpp
beresta::Element copy = *book;                                  // глубокая копия на стеке
auto heap = std::make_unique<beresta::Element>(*book);          // в куче
std::unique_ptr<beresta::Node> any = node->clone();             // полиморфно, тип сохраняется
std::unique_ptr<beresta::Element> shell = book->cloneShallow(); // имя и атрибуты, без детей

*target = source;     // содержимое заменяется глубокой копией, место target в дереве не меняется
```

Копия **автономна** (`getParent() == nullptr`) и не делит с оригиналом ни одного узла. Перенос без копирования:

```cpp
targetParent->appendChild(sourceParent->removeChild(index));
```

Узел, извлечённый из документа, переживает сам документ.

Из других языков то же самое делают `beresta_node_move_to` и методы обёрток рядом с копированием:

| Язык | Копия | Перенос без копирования |
|---|---|---|
| C | `beresta_node_copy_to(node, parent, &copy)` | `beresta_node_move_to(node, parent)` |
| Java | `node.copyTo(parent)` | `node.moveTo(parent)` |
| C# | `node.CopyTo(parent)` | `node.MoveTo(parent)` |
| Python | `node.copy_to(parent)` | `node.move_to(parent)` |
| Node.js, WebAssembly | `node.copyTo(parent)` | `node.moveTo(parent)` |

```python
source = beresta.parse("<a><item><name>Мёд</name></item></a>")
target = beresta.parse("<b/>")
item = source.root.first_child
name = item.first_child          # обёртка потомка, полученная до переноса
item.move_to(target.root)        # узел (с потомками) теперь принадлежит target
source.close()                   # закрытие прежнего документа узел не трогает
print(name.text, item.document is target)   # Мёд True
```

Перенос ставит узел в конец детей `parent` — элемента или документа (в документе без корня элемент становится корнем). Дескриптор узла и дескрипторы его потомков не меняются: объект не копируется, им просто начинает владеть новый документ. В обёртках у каждого узла одна обёртка (реестр документа), поэтому документ-владелец меняется у всех уже выданных обёрток поддерева: после переноса их срок жизни определяет новый документ, а не прежний. Нельзя перенести сам документ (`INVALID_ARGUMENT`), корневой элемент документа и узел внутрь самого себя или своего потомка (`HIERARCHY_VIOLATION`). Если новый родитель не принимает узел (например, текст на верхний уровень документа), возвращается `HIERARCHY_VIOLATION`, а дерево остаётся прежним.

## Разбор: DOM

```cpp
beresta::XmlParser parser(options);
beresta::Document a = parser.parse(text);                   // из памяти
beresta::Document b = parser.parseFile("data.xml");         // из файла (baseUri = путь)
beresta::Document c = parser.parse(stream);                 // std::istream
std::unique_ptr<beresta::Element> e = parser.parseElement("<x a='1'/>");   // автономный фрагмент
```

Вход — **байты** в любой поддерживаемой кодировке: она определяется по BOM и XML-декларации.

### `ParserOptions`

| Поле | По умолчанию | Назначение |
|---|---|---|
| `preserveWhitespaceText` | `false` | сохранять текст из одних пробелов (отступы) |
| `discardComments` | `false` | не добавлять комментарии в DOM |
| `coalesceCData` | `false` | превращать CDATA в обычный текст |
| `trackLocations` | `false` | записывать строку и столбец каждого узла |
| `namespaceAware` | `true` | проверять правила Namespaces in XML |
| `validateDtd` | `false` | проверять документ по DTD |
| `loadExternalDtd` | `false` | загружать внешний DTD (нужен `resolver`) |
| `applyDtdDefaults` | `true` | добавлять атрибуты по умолчанию из `<!ATTLIST>` |
| `processXInclude` | `false` | выполнять `xi:include` (нужен `resolver`) |
| `maxDepth` | `1024` | максимальная вложенность элементов |
| `maxEntityExpansions` | `10000` | максимальное число раскрытий сущностей |
| `maxEntityDepth` | `16` | вложенность сущностей (и XInclude) |
| `maxExpandedSize` | 10 МБ | суммарный объём текста из сущностей |
| `forcedEncoding` | `""` | принудительная кодировка входа |
| `baseUri` | `""` | база для относительных ссылок |
| `resolver` | `nullptr` | загрузчик внешних ресурсов |
| `errorHandler` | `nullptr` | получатель ошибок и предупреждений |
| `schema` | `nullptr` | XML Schema для проверки во время разбора (DOM и SAX) |

`resolver` и `errorHandler` — **невладеющие** указатели: объекты должны жить, пока идёт разбор.

### Пробелы

Текст **только из пробелов** между тегами по умолчанию отбрасывается: это форматирование, и благодаря этому «красивый» и «сплошной» XML дают одно и то же дерево. Текст, в котором есть хоть один непробельный символ или символьная ссылка, сохраняется дословно. Для смешанной разметки (`<b>a</b> <i>b</i>`) включите `preserveWhitespaceText`.

### Позиции узлов

```cpp
beresta::ParserOptions options;
options.trackLocations = true;
beresta::Document doc = beresta::XmlParser(options).parse(text);
std::size_t line = doc.getRoot()->getSourceLocation().line;
```

Узел из раскрытой сущности получает позицию ссылки на эту сущность в исходном файле.

## Разбор: SAX

Потоковый разбор: дерево не строится, расход памяти не зависит от размера документа.

```cpp
class PriceCounter : public beresta::ContentHandler
{
public:
    void startElement(const beresta::SaxElement& e) override { inside = e.localName == "price"; }
    void characters(std::string_view text) override { if (inside) total += beresta::xpath::stringToNumber(text); }
    void endElement(const beresta::SaxElement&) override { inside = false; }

    bool inside = false;
    double total = 0;
};

PriceCounter counter;
beresta::SaxParser(options).parseFile("big.xml", counter);
```

| Событие | Когда |
|---|---|
| `setDocumentLocator(const Locator&)` | до начала; `locator.getLocation()` даёт позицию текущего события |
| `startDocument()` / `endDocument()` | начало и конец |
| `xmlDeclaration(const XmlDeclaration&)` | декларация |
| `documentType(const DocumentType&)` | DOCTYPE вместе с моделью DTD |
| `startElement(const SaxElement&)` / `endElement(...)` | теги: `name`, `namespaceUri`, `localName`, `attributes` |
| `characters(text)` / `cdata(text)` | текст (сущности уже раскрыты) / CDATA |
| `ignorableWhitespace(text)` | пробелы между тегами |
| `comment(text)` / `processingInstruction(target, data)` | комментарии и PI |
| `dtdProcessingInstruction(target, data)` | PI из внутреннего и внешнего DTD, до `documentType`; по умолчанию вызывает `processingInstruction` (раздел 2.6: PI передаются приложению). `DomBuilder` их пропускает |

Все `string_view` в событиях действительны **только на время вызова**. `DomBuilder` — открытый обработчик, строящий DOM; его можно унаследовать.

С `options.schema` документ по ходу разбора проверяется по XML Schema потоковым валидатором, а ваш обработчик получает те же события; дерево при этом не строится (см. [XML Schema](#xml-schema)).

## Пространства имён

При разборе (`namespaceAware = true`) проверяется: префиксы объявлены, `xml`/`xmlns` не переопределены, имена корректны, нет двух атрибутов с одним расширенным именем. Нарушение даёт фатальную ошибку `NAMESPACE_ERROR`.

В DOM URI вычисляются **«вживую»** по объявлениям `xmlns` в предках. Поэтому они всегда соответствуют тому, что будет записано в файл, даже после переноса элемента.

```cpp
const beresta::Element* body = envelope->findChildElementNS("http://schemas.xmlsoap.org/soap/envelope/", "Body");
body->getPrefix();                  // "soap"
body->getLocalName();               // "Body"
body->getNamespaceURI();            // optional<string>
body->lookupNamespaceURI("soap");
body->lookupPrefix("urn:x");
doc.getElementsByTagNameNS("urn:x", "*");

element.declareNamespace("x", "urn:x");             // xmlns:x="urn:x"
element.setAttributeNS("urn:x", "x:flag", "1");     // объявит префикс сам, если нужно
element.getAttributeNS("urn:x", "flag");
element.removeAttributeNS("urn:x", "flag");
```

## Кодировки, файлы и потоки

Определение кодировки входа:
1. BOM (UTF-8, UTF-16LE, UTF-16BE).
2. Сигнатура `<?` в UTF-16 без BOM.
3. Атрибут `encoding` в декларации (`<?xml` и сразу пробел; `<?xml-stylesheet ...?>` — обычная PI).
4. Иначе UTF-8.

Если кодировку определили BOM или сигнатура UTF-16, а декларация называет другую (BOM UTF-8 и `encoding="iso-8859-1"`), это ошибка `ENCODING_ERROR` (раздел 4.3.3). Концы строк (`\r\n`, `\r`) нормализуются один раз — при декодировании документа, внешнего DTD или сущности; символ `\r` из ссылки `&#13;` сохраняется.

`ParserOptions::forcedEncoding` перекрывает автоопределение (и проверку согласия с декларацией). Байты, недопустимые в кодировке, и символы, запрещённые в XML (управляющие коды и т.п.), дают ошибку `ENCODING_ERROR` с позицией.

| Кодировка | Имена |
|---|---|
| UTF-8 | `UTF-8`, `utf8` |
| UTF-16 | `UTF-16` (с BOM), `UTF-16LE`, `UTF-16BE` |
| Латиница | `ISO-8859-1` (`latin1`), `US-ASCII`, `windows-1252` (`cp1252`) |
| Кириллица | `windows-1251` (`cp1251`), `KOI8-R`, `IBM866` (`cp866`) |

```cpp
const beresta::encoding::Charset* cp1251 = beresta::encoding::findCharset("cp1251");

std::string bytes = beresta::io::readFile("in.xml");    // двоичное чтение, путь — std::filesystem::path
beresta::io::writeFile("out.xml", bytes);
beresta::io::readStream(std::cin);
```

## Сериализация

```cpp
std::string utf8 = node.toString();     // компактно, всегда UTF-8
node.serialize(buffer);                 // дописать в существующий буфер

beresta::SerializerOptions options;
options.prettyPrint = true;              // отступы
options.indent = "  ";
options.newline = "\n";
options.encoding = "windows-1251";       // кодировка результата
options.writeDeclaration = true;         // писать декларацию (если она была или кодировка не UTF-8)
options.forceDeclaration = false;        // писать даже для документа без декларации

beresta::XmlSerializer serializer(options);
std::string bytes = serializer.toString(doc);
serializer.write(doc, stream);
serializer.writeFile(doc, "out.xml");
```

Правила:
- Компактный вывод не содержит ни одного лишнего пробела, а порядок атрибутов сохраняется.
- При `prettyPrint` каждый ребёнок элемента, содержащего только элементы, идёт с новой строки. Элементы с текстом выводятся дословно, поэтому повторный разбор даёт то же дерево.
- `encoding` в декларации всегда соответствует фактической кодировке вывода. Для `UTF-16` пишется BOM. Символы вне кодировки становятся `&#N;`.
- DOCTYPE выводится в минимальной форме: `<!DOCTYPE r SYSTEM "r.dtd"[...]>`.

## DTD и сущности

```cpp
const char* xml =
    "<!DOCTYPE r [<!ENTITY who \"мир\"><!ENTITY bold \"<b>&who;</b>\">"
    "<!ATTLIST r lang CDATA \"ru\">]><r>Привет, &bold;</r>";
beresta::Document doc = beresta::XmlParser().parse(xml);
doc.getRoot()->getAttribute("lang");      // "ru" — значение по умолчанию из ATTLIST
doc.toString();                            // DOCTYPE сохраняется, сущности раскрыты
```

- **Сущности** — внутренние (с разметкой внутри), внешние (через `resolver`), параметрические `%pe;`, в том числе внутри объявлений во внешнем подмножестве. Работают условные секции `INCLUDE`/`IGNORE`.
- **Атрибуты по умолчанию** и нормализация значений не-CDATA атрибутов выполняются как в Xerces.
- **Модель DTD** доступна через `doc.getDocumentType()->getModel()`: объявления сущностей, элементов, атрибутов и нотаций.
- **Внешняя PE во внутреннем подмножестве** читается по правилам внешнего подмножества (ссылки `%pe;` внутри объявлений, условные секции); относительный `SYSTEM` сущности разрешается от того текста, где она объявлена.
- **Необъявленная сущность.** В документе без внешнего DTD и без ссылок `%pe;` (или со `standalone="yes"`) это фатальная ошибка; иначе — ошибка валидности (если проверка включена), а ссылка пропускается (раздел 4.1). При `standalone="yes"` ссылаться на сущность, объявленную во внешнем DTD, нельзя.
- **Проверка валидности** (`validateDtd = true`) проверяет:
  - корень и объявленность элементов и атрибутов;
  - `#REQUIRED` и `#FIXED`;
  - типы `ID`, `IDREF(S)`, `NMTOKEN(S)`, `ENTITY(IES)`, перечисления, уникальность ID и цели IDREF; с пространствами имён значения ID/IDREF/ENTITY не содержат `:`;
  - модели `EMPTY` (внутри нельзя даже комментарий, PI и ссылку на пустую сущность), `ANY`, `MIXED` и `CHILDREN`;
  - сами объявления: повторное объявление элемента, повтор имени в смешанном содержимом, один ID- и один NOTATION-атрибут на элемент, умолчание ID-атрибута, объявленность нотаций, повторы в перечислениях, лексическая допустимость значений по умолчанию;
  - вложенность скобок групп, объявлений и условных секций в параметрических сущностях;
  - `standalone="yes"`: результат не должен зависеть от внешнего DTD (умолчания, нормализация, пробелы в элементном содержимом).

```cpp
beresta::CollectingErrorHandler handler;
beresta::ParserOptions options;
options.validateDtd = true;
options.errorHandler = &handler;
beresta::XmlParser(options).parse(text);
for (const beresta::Diagnostic& d : handler.getDiagnostics())
    std::cout << d.message << '\n';       // все ошибки за один проход
```

Без `errorHandler` первая ошибка валидности бросает `ParseException` с кодом `VALIDATION_ERROR`.

## XML Schema

```cpp
// Загрузка схемы (один раз; схема неизменяема и разделяется между потоками)
std::shared_ptr<const beresta::xsd::Schema> schema = beresta::xsd::Schema::fromFile("catalog.xsd", loadOptions);

// Вариант 1: отдельная проверка готового DOM
beresta::xsd::SchemaValidator validator(schema);
std::vector<beresta::Diagnostic> errors = validator.validate(doc);
bool ok = validator.isValid(doc);

// Вариант 2: проверка прямо при разборе в DOM — один проход, без второго обхода дерева
beresta::ParserOptions options;
options.schema = schema;
options.errorHandler = &handler;          // без него — исключение на первой ошибке
beresta::XmlParser(options).parseFile("catalog.xml");

// Вариант 3: потоковая проверка без дерева — для выгрузок в гигабайты
MyHandler events;                         // любой ContentHandler (или пустой)
beresta::SaxParser(options).parseFile("export.xml", events);
```

Каждая ошибка содержит путь к элементу и позицию: `строка 12, столбец 5: /catalog/book[2]/price: значение "-5" меньше минимума 0`. Позиции ошибок есть всегда: валидатор берёт их у парсера, а узлам дерева они записываются, только если включён `trackLocations`.

**Проверка во время разбора.** Валидатор — декоратор над потоком событий SAX (`xsd::ValidatingHandler`): события проходят через него и уходят дальше — в `DomBuilder`, в ваш обработчик или никуда. Модель содержимого сверяется пошагово, по одному ребёнку (жадный проход для последовательностей из разных элементов, автомат на конфигурациях частиц для остальных моделей), простые значения — при закрытии элемента по накопленному тексту. Все три варианта — одна и та же логика проверки: `SchemaValidator::validate` превращает готовое дерево в поток событий обходом без рекурсии. Поэтому ошибки, их порядок, пути и позиции во всех трёх вариантах совпадают.

- **DOM со схемой** (`XmlParser`): документ проверяется за тот же проход, что и строится; ключи `xs:key`/`xs:unique`/`xs:keyref` — по готовому дереву, тем же движком XPath. С `processXInclude` документ проверяется уже после подстановки включений, по дереву.
- **SAX со схемой** (`SaxParser`): дерево не строится, память проверки — O(глубины документа) плюс значения ID и таблицы ключей. Ключи вычисляются потоково (см. ниже). Ошибки приходят в `errorHandler` после `endDocument`: номера в путях вида `item[5]` известны, только когда дочитаны все соседи.
- **Свой конвейер:** `ValidatingHandler` можно поставить перед любым обработчиком вручную.

```cpp
beresta::DomBuilder builder(options);
beresta::xsd::ValidatingHandler validator(schema, &builder,
    beresta::xsd::validationSettingsFor(options, beresta::xsd::IdentityEvaluation::ON_TREE));
beresta::SaxParser(parserOptionsWithoutSchema).parse(text, validator);
beresta::Document doc = builder.takeDocument();
validator.checkIdentity(doc);                                // ключи — по построенному дереву
std::vector<beresta::Diagnostic> errors = validator.takeDiagnostics();
```

| Загрузка | Описание |
|---|---|
| `Schema::fromString(text, options)` | из текста XSD |
| `Schema::fromFile(path, options)` | из файла (`baseUri` = путь) |
| `Schema::fromDocuments({&a, &b}, options)` | несколько схем разных пространств имён |
| `SchemaLoadOptions::resolver` | загрузчик для `xs:include` / `xs:import` |

**Поддерживается:**
- `targetNamespace`, `elementFormDefault`/`attributeFormDefault`, `form`;
- глобальные и локальные элементы и атрибуты, `ref`, анонимные типы;
- `complexType` с `sequence`/`choice`/`all`, вложенными группами, `minOccurs`/`maxOccurs`, `mixed`;
- `complexContent` `extension`/`restriction`, `simpleContent` `extension`/`restriction`;
- `xs:group`, `xs:attributeGroup`, `xs:any` (`##any`, `##other`, `##local`, `##targetNamespace`, список; `strict`/`lax`/`skip`), `xs:anyAttribute`;
- атрибуты: `use="required|optional|prohibited"`, `default`, `fixed`;
- элементы: `default`, `fixed`, `nillable` + `xsi:nil`, `abstract`, `xsi:type`;
- группы замены `substitutionGroup`: члены (в том числе транзитивные) стоят на месте головы и проверяются по своему объявлению; абстрактные члены и заблокированные `block` в группу не входят;
- наследование: тип из `xsi:type` обязан быть выведен из объявленного (цепочки встроенных типов, `extension`/`restriction`, члены `union`), `block`/`blockDefault` у элемента и типа запрещают способы замены, `final`/`finalDefault` запрещают наследование при загрузке схемы; абстрактный тип без производного `xsi:type` — ошибка;
- `simpleType` `restriction`/`list`/`union`;
- фасеты `length`, `minLength`, `maxLength`, `pattern`, `enumeration`, `whiteSpace`, `minInclusive`, `maxInclusive`, `minExclusive`, `maxExclusive`, `totalDigits`, `fractionDigits`;
- все **45 встроенных типов** XSD 1.0 (строковые, целые с точными границами, `decimal`, `float`/`double`, даты и время с часовыми поясами, `duration`, `hexBinary`, `base64Binary`, `QName`, ID/IDREF(S), NMTOKEN(S), ENTITY(IES) и т.д.);
- уникальность `ID` и существование целей `IDREF`;
- ограничения идентичности `xs:unique`, `xs:key`, `xs:keyref` (подробности ниже);
- `xs:include` (включая «хамелеонные» схемы), `xs:import`, `xs:redefine` и `xs:override` (из XSD 1.1: подмена компонента целиком).

**Группы замены и `xs:redefine` не замедляют проверку.** Подмена компонентов через `xs:redefine` / `xs:override` происходит в реестре определений до построения моделей — проверяемый документ о ней не знает. Множество допустимых заменителей каждой головы вычисляется один раз при загрузке схемы (транзитивно, с учётом `abstract`, `block` и `final`) и хранится упорядоченным: имя ребёнка ищется двоичным поиском, только если оно не совпало с самой частицей. Признак группы стоит на частице модели, поэтому модели без групп замены по-прежнему идут быстрым жадным путём.

```xml
<!-- v2.xsd: новая версия отраслевой схемы без правки исходной -->
<xs:redefine schemaLocation="v1.xsd">
    <xs:complexType name="Party">
        <xs:complexContent>
            <xs:extension base="Party">          <!-- base — прежний Party из v1.xsd -->
                <xs:sequence><xs:element name="inn" type="xs:string"/></xs:sequence>
            </xs:extension>
        </xs:complexContent>
    </xs:complexType>
</xs:redefine>
```

### Ограничения идентичности: xs:key, xs:unique, xs:keyref

Реляционные проверки внутри документа выполняются силами самой схемы, без кода на стороне приложения:

```xml
<xs:element name="shop">
    <xs:complexType>...</xs:complexType>
    <!-- артикул товара обязателен и уникален в магазине -->
    <xs:key name="productKey">
        <xs:selector xpath="s:product"/>
        <xs:field xpath="s:sku"/>
    </xs:key>
    <!-- штрихкод необязателен, но если есть — уникален -->
    <xs:unique name="eanUnique">
        <xs:selector xpath="s:product"/>
        <xs:field xpath="@ean"/>
    </xs:unique>
    <!-- каждый заказ ссылается на существующий товар -->
    <xs:keyref name="orderRef" refer="s:productKey">
        <xs:selector xpath="s:order"/>
        <xs:field xpath="@sku"/>
    </xs:keyref>
</xs:element>
```

```
/shop/product[3]: значение (1) повторяется: нарушено ограничение xs:key "productKey"
/shop/order[2]: keyref "orderRef": значение (7) не найдено среди значений ключа "productKey"
```

- **Сравнение по значению типа**, а не по строке: для `xs:decimal` значения `1`, `1.0` и `01` — один ключ, для `xs:boolean` совпадают `1` и `true`, даты сравниваются с учётом часового пояса. Тип поля берётся из проверки документа: тип атрибута или простой тип элемента. Канонический вид значения доступен и напрямую: `beresta::xsd::canonicalValue(type, value)`.
- **Составные ключи** из нескольких `xs:field`, поля-атрибуты и поля-элементы, селекторы на любой глубине (`.//item`) и объединения (`a | b`).
- **Правила спецификации:** у `xs:key` каждое поле обязано быть, у `xs:unique` строки без значений пропускаются, поле не может выбирать больше одного узла или элемент со сложным содержимым.
- **Области видимости:** таблица ключей строится для каждого элемента с объявленным ограничением, а `xs:keyref` находит ключ, объявленный на том же элементе или на его потомках.
- **Ошибки схемы ловятся при загрузке:** необъявленный `refer`, ссылка `keyref` на другой `keyref`, разное число полей у `keyref` и ключа, повтор имени ограничения, синтаксическая ошибка в `xpath`.
- Префиксы в `xpath` разрешаются по объявлениям `xmlns` документа схемы. Имя без префикса, как и положено в XSD 1.0, — вне пространств имён.
- Селекторы и поля компилирует тот же движок XPath 1.0 один раз при загрузке схемы. Он принимает и выражения сверх грамматики XSD, которую реальные схемы и так соблюдают.
- **Потоково (SAX без дерева)** ключи проверяются, как в Xerces: селекторы и поля из грамматики XSD (оси `child` и `attribute`, `.//` в начале, `|`, `*`, `p:*`) сопоставляются со стеком имён открытых элементов, строка ключа собирается к закрытию целевого элемента, таблицы и ссылки — к закрытию области. Сообщения те же, что и при проверке по дереву. Ограничение с выражением вне этой грамматики (например, `a//b` или с предикатом) без дерева не проверить — об этом приходит одно сообщение на ограничение.

Простые типы доступны и без схемы:

```cpp
const beresta::xsd::SimpleType* type = beresta::xsd::builtinType("dateTime");
std::optional<std::string> error = beresta::xsd::validateSimpleValue(*type, "2026-10-17T12:00:00+03:00", nullptr);
bool equal = beresta::xsd::valuesEqual(*beresta::xsd::builtinType("decimal"), "1.0", "001");   // true
```

## XPath 1.0

```cpp
// Быстрые обёртки
std::vector<beresta::Element*> books = beresta::xpath::selectElements(doc, "//book[price > 300]");
std::string title = beresta::xpath::evaluateString(doc, "string(//book[1]/title)");

// Скомпилированное выражение: многократно и из разных потоков
beresta::xpath::XPathExpression expression("//s:item[@code = $code]/s:name");
beresta::xpath::XPathContext context;
context.namespaces.emplace("s", "urn:shop");
context.variables.emplace("code", beresta::xpath::XPathValue::fromString("B2"));

beresta::xpath::XPathValue value = expression.evaluate(doc, context);
value.getType();          // NODE_SET, BOOLEAN, NUMBER, STRING
value.getNodes();         // XPathItem{node, attribute, owner, isNamespace} в порядке документа
value.toString(); value.toNumber(); value.toBoolean();
expression.selectElements(doc, context);
```

- **Оси (все 13):** `child`, `descendant`, `descendant-or-self`, `parent`, `ancestor`, `ancestor-or-self`, `following-sibling`, `preceding-sibling`, `following`, `preceding`, `attribute`, `namespace`, `self`, а также сокращения `//`, `.`, `..`, `@`.
- **Ось `namespace`** возвращает по узлу на каждый префикс, действующий на элементе: объявления самого элемента и его предков (ближайшее скрывает дальние), отмена `xmlns=""` и неявный префикс `xml`. Имя узла — префикс, строковое значение — URI, `namespace-uri()` пуст, родитель — элемент. В порядке документа узлы пространств имён идут после элемента и до его атрибутов. В `XPathItem` у такого узла `isNamespace == true`, `attribute` указывает на объявление `xmlns:p`, `owner` — на элемент. Объявления `xmlns`, как и требует XPath, атрибутами не считаются.
- **Проверки узлов:** имена, `*`, `p:*`, `node()`, `text()`, `comment()`, `processing-instruction('t')`.
- **Выражения:** предикаты (числовые = позиция), `|`, `or`, `and`, `=`, `!=`, `<`, `<=`, `>`, `>=`, `+`, `-`, `*`, `div`, `mod`, унарный минус. Сравнения множеств работают по правилам спецификации.
- **Функции (все 27):** `last`, `position`, `count`, `id`, `local-name`, `namespace-uri`, `name`, `string`, `concat`, `starts-with`, `contains`, `substring-before`, `substring-after`, `substring`, `string-length`, `normalize-space`, `translate`, `boolean`, `not`, `true`, `false`, `lang`, `number`, `sum`, `floor`, `ceiling`, `round`.
- Строковые функции считают **символы Unicode**, а не байты. Числа выводятся по правилам XPath: `0.1 + 0.2` = `0.30000000000000004`, `1 div 0` = `Infinity`.
- Как и в XPath 1.0, имя **без префикса** означает «вне пространств имён». Для документа с `xmlns="..."` свяжите префикс в `XPathContext`.

## Обход дерева: TreeWalker и NodeIterator

```cpp
class SkipDrafts : public beresta::NodeFilter
{
public:
    beresta::FilterResult acceptNode(const beresta::Node& node) const override
    {
        const auto& element = static_cast<const beresta::Element&>(node);
        if (element.getAttribute("draft") == "yes")
            return beresta::FilterResult::REJECT;     // скрыть вместе с поддеревом
        return beresta::FilterResult::ACCEPT;          // SKIP — скрыть узел, но показать детей
    }
};

SkipDrafts filter;
beresta::TreeWalker walker(*doc.getRoot(), beresta::show::ELEMENTS, &filter);
for (beresta::Node* n = walker.nextNode(); n != nullptr; n = walker.nextNode()) { /* ... */ }
walker.parentNode(); walker.firstChild(); walker.lastChild();
walker.nextSibling(); walker.previousSibling(); walker.previousNode();

beresta::NodeIterator texts(doc, beresta::show::TEXTS);
for (beresta::Node* t = texts.nextNode(); t != nullptr; t = texts.nextNode()) { /* ... */ }
```

Маски `show::`: `ALL_NODES`, `DOCUMENTS`, `DOCUMENT_TYPES`, `ELEMENTS`, `TEXTS`, `CDATA_SECTIONS`, `COMMENTS`, `PROCESSING_INSTRUCTIONS` (комбинируются через `|`). Алгоритмы соответствуют DOM Level 2 Traversal, включая различие `SKIP` и `REJECT`.

## Внешние ресурсы и безопасность

По умолчанию **ничего внешнего не загружается**: ни внешний DTD, ни внешние сущности, ни XInclude, ни `xs:include`. Это закрывает XXE и SSRF. Чтобы разрешить загрузку, передайте резолвер:

```cpp
beresta::FileResourceResolver resolver("C:/data/xml");   // только локальные файлы внутри корня
options.resolver = &resolver;
options.loadExternalDtd = true;
```

`FileResourceResolver` разрешает относительные пути от `baseUri`, отвергает сетевые URI (`http:`, `https:`, `ftp:` и т.п.) и пути, выходящие за корень через `..`.

Свой загрузчик (кэш, архив, база данных) — это наследник `ResourceResolver` с методом `resolve(const ResourceRequest&)`. Запрос содержит `kind` (`EXTERNAL_DTD`, `EXTERNAL_ENTITY`, `XINCLUDE`, `SCHEMA`), `publicId`, `systemId` и `baseUri`.

Лимиты `maxEntityExpansions`, `maxEntityDepth`, `maxExpandedSize` и `maxDepth` защищают от «сущностных бомб» и чрезмерно глубоких документов. Превышение лимита — ошибка `LIMIT_EXCEEDED`.

От атак на сложность алгоритмов защита встроена: хеш-таблицы с ключами из документа (значения ID, имена) используют SipHash-1-3 со случайным ключом процесса (`utils::SeededHash`), а повторы атрибутов и расширенных имён ищутся за O(1) даже на теге с сотнями тысяч атрибутов. Пакетная установка атрибутов `Element::setAttributes` тоже линейна. Порядок обхода таких таблиц от запуска к запуску меняется, поэтому они используются только для поиска и никогда — для вывода: результат разбора и сериализации детерминирован.

## Языки сообщений

Тексты ошибок не разбросаны по коду строковыми литералами: каждое сообщение — константа `beresta::i18n::Message` (`include/i18n/message.hpp`, 302 сообщения), а тексты лежат в каталогах языков `src/i18n/catalogs/`. В комплекте два языка: русский (`ru`) и английский (`en`).

```
[PARSE_ERROR] строка 1, столбец 7: ожидался </b>, найден </a>     ← ru
[PARSE_ERROR] line 1, column 7: expected </b>, found </a>          ← en
```

Имя кода ошибки (`PARSE_ERROR`, `VALIDATION_ERROR`...) одинаково во всех языках, поэтому программная обработка ошибок от языка не зависит.

**Язык по умолчанию** выбирается при сборке. Неизвестный код останавливает сборку с понятной ошибкой:

```bash
make ERRORS_LANG=en
```
```bash
cmake -S . -B build -DBERESTA_ERRORS_LANG=en
```

**Во время работы** язык меняется одним вызовом — сразу для всех потоков. Неизвестный код отвергается, и язык остаётся прежним:

| Язык | Сменить | Текущий | Все языки |
|---|---|---|---|
| C++ | `beresta::i18n::setLanguage("en")` (→ `bool`) | `beresta::i18n::language()` | `beresta::i18n::availableLanguages()` |
| C | `beresta_set_language("en")` (→ `BERESTA_INVALID_ARGUMENT`, если языка нет) | `beresta_language()` | `beresta_languages()` → `"ru,en"` |
| Java | `Languages.use("en")` | `Languages.current()` | `Languages.available()` |
| C# | `BerestaLibrary.Language = "en"` | `BerestaLibrary.Language` | `BerestaLibrary.Languages` |
| Python | `beresta.set_language("en")` | `beresta.language()` | `beresta.languages()` |
| Node.js, WebAssembly | `beresta.setLanguage('en')` | `beresta.language()` | `beresta.languages()` |

Собственные сообщения обёрток («документ уже закрыт» и т.п.) тоже берутся из общего каталога через `beresta_message_text`: язык, добавленный в библиотеку, обёртки подхватывают без изменений.

Шаблоны сообщений содержат метки `{0}`, `{1}`... — их порядок в переводе может быть любым; `{{0}}` выводит аргумент в фигурных скобках (так записываются имена вида `{urn:shop}item`). Если в каталоге языка нет какого-то текста, используется английский.

```cpp
std::string text = beresta::i18n::format(beresta::i18n::Message::LIMIT_DEPTH, {"1024"});
```

### Как добавить язык

1. Скопируйте `src/i18n/catalogs/messages_en.cpp` в `messages_<код>.cpp` (например, `messages_de.cpp`) и переведите тексты, сохраняя метки `{N}`.
2. В конце файла переименуйте каталог: `const Catalog GERMAN_CATALOG{"de", "Deutsch", TEXTS, ...};`.
3. Объявите его в `include/i18n/i18n.hpp` (`extern const Catalog GERMAN_CATALOG;`) и добавьте строку `&GERMAN_CATALOG` в реестр `catalogs()` в `src/i18n/i18n_registry.cpp`.

Больше ничего менять не нужно: Makefile и CMake находят каталоги сами, поэтому сразу работают `make ERRORS_LANG=de` и `-DBERESTA_ERRORS_LANG=de`, а `Languages.use("de")` и аналоги — во всех обёртках.

## Гарантии и потокобезопасность

- **Строгая гарантия исключений** у `appendChild`, `insertChild`, `replaceChild`, `setRoot`, `set*`-методов, `setAttributes` (имена проверяются до изменений) и копирующего присваивания: при ошибке ничего не меняется.
- **`XmlParser`, `SaxParser`, `XmlSerializer`, `XPathExpression`, `Schema`, `SchemaValidator`** неизменяемы: один объект можно одновременно использовать из многих потоков (если ваши `resolver` и `errorHandler` тоже потокобезопасны).
- **Разные деревья** можно обрабатывать параллельно без синхронизации. **Одно дерево** можно читать из многих потоков через `const`-методы. Если хотя бы один поток его меняет, нужна внешняя синхронизация.

## Другие языки: Си-интерфейс

Заголовок `include/capi/beresta_c.h` написан на C99 и подключается и в `.c`, и в `.cpp`. На нём построены все обёртки, и им же можно пользоваться напрямую из C, Go (cgo), Rust (FFI), Delphi и любого языка, который умеет вызывать функции C.

```c
#include "capi/beresta_c.h"

const char* xml = "<shop><item code=\"A1\">Чай</item><item code=\"B2\">Кофе</item></shop>";
beresta_document document = NULL;
beresta_xpath xpath = NULL;

if (beresta_document_parse(xml, (int64_t)strlen(xml), BERESTA_PARSE_DEFAULT, NULL, &document) != BERESTA_OK)
{
    fprintf(stderr, "[%s] %s\n", beresta_status_name(beresta_last_error_code()), beresta_last_error_message());
    return 1;
}
beresta_xpath_compile("//item[@code = $code]", &xpath);
beresta_xpath_set_string(xpath, "code", "B2");

char* name = beresta_xpath_string(xpath, document);   /* "Кофе" */
printf("%s\n", name);
beresta_string_free(name);                             /* строку освобождает библиотека */

beresta_xpath_free(xpath);
beresta_document_free(document);                       /* документ вместе со всеми узлами */
```

Полный пример — `examples/capi/capi_demo.c` (собирается вместе с демо). Подключение к своей программе:

```bash
gcc -std=c99 -Ipath/to/beresta/include app.c -Lpath/to/beresta/bin -lberesta -o app
```

Флаги разбора — битовая маска `BERESTA_PARSE_*`: `PRESERVE_WHITESPACE`, `DISCARD_COMMENTS`, `COALESCE_CDATA`, `VALIDATE_DTD`, `NO_NAMESPACES`, `XINCLUDE`, `FILE_RESOURCES`, `TRACK_LOCATIONS`. `FILE_RESOURCES` разрешает внешние DTD, сущности и XInclude, но только из каталога разбираемого файла. `TRACK_LOCATIONS` запоминает строку и столбец каждого узла: тогда `schema_validate` сообщает места нарушений (без флага — 0; разбор с ним примерно на 8 % медленнее).

**Потоковая проверка без дерева.** `beresta_schema_validate_bytes` и `beresta_schema_validate_file` принимают те же аргументы, что `beresta_document_parse` и `beresta_document_parse_file`, но вместо документа возвращают список нарушений. Внутри работает SAX-парсер с `ValidatingHandler`: дерево не строится, память — O(глубины документа) плюс значения ID и таблицы ключей, а файл отображается в память, а не копируется. Нарушения схемы — не ошибка вызова (`BERESTA_OK` и список), синтаксическая ошибка XML — `BERESTA_PARSE_ERROR`. Места нарушений известны всегда, флаг `TRACK_LOCATIONS` не нужен.

```c
beresta_diagnostics problems = NULL;
if (beresta_schema_validate_file("export.xml", BERESTA_PARSE_DEFAULT, schema, &problems) == BERESTA_OK)
{
    for (int64_t i = 0; i < beresta_diagnostics_count(problems); ++i)
    {
        char* text = beresta_diagnostics_message(problems, i);
        printf("%lld: %s\n", (long long)beresta_diagnostics_line(problems, i), text);
        beresta_string_free(text);
    }
    beresta_diagnostics_free(problems);
}
``` Флаги вывода — `BERESTA_WRITE_PRETTY` и `BERESTA_WRITE_DECLARATION`. Маска выбрана вместо структуры настроек сознательно: целое число одинаково передаётся из любого языка.

Коды 1–15 совпадают с `DomErrorCode` + 1 (`BERESTA_PARSE_ERROR`, `BERESTA_VALIDATION_ERROR`...). Ещё три кода есть только в Си-интерфейсе: `BERESTA_INVALID_ARGUMENT` (NULL или дескриптор не того типа), `BERESTA_OUT_OF_MEMORY`, `BERESTA_UNKNOWN_ERROR`.

## Java (Project Panama)

Обёртка — Maven-проект `bindings/java` (пакет `org.beresta`, Java 22+). Она использует Foreign Function & Memory API: JNI, заголовков `jni.h` и кода на C для связки нет. Зависимостей тоже нет.

```java
import org.beresta.*;

try (XmlDocument document = Xml.parse("<shop><item code='A1'>Чай</item></shop>"))
{
    XmlElement item = (XmlElement) document.root().firstChild();
    System.out.println(item.getAttribute("code") + " " + item.text());       // A1 Чай

    try (XPath query = new XPath("//item[@code = $c]"))
    {
        System.out.println(query.set("c", "A1").string(document));            // Чай
    }
}

try (XmlDocument order = XmlDocument.create("order"))
{
    XmlElement item = order.root().appendElement("item");
    item.setAttribute("qty", "2");
    item.appendText("Мёд & орехи");
    System.out.println(order.toXml());   // <order><item qty="2">Мёд &amp; орехи</item></order>
    order.save(Path.of("order.xml"), WriteFlags.PRETTY, "windows-1251");
}

try (XmlSchema schema = XmlSchema.fromFile(Path.of("order.xsd"));
     XmlDocument document = Xml.parseFile(Path.of("order.xml"), ParseFlags.TRACK_LOCATIONS, null))
{
    for (Diagnostic problem : schema.validate(document))                    // готовое дерево
        System.out.println(problem.line() + ": " + problem.message());
    List<Diagnostic> export = schema.validateFile(Path.of("export.xml"));   // поток без дерева, хоть гигабайты
}
catch (BerestaException error)
{
    System.out.println(error.codeName() + " " + error.detail());           // PARSE_ERROR строка 1, ...
}
```

Как это устроено:
- `NativeLoader` определяет платформу по `os.name` и `os.arch`, извлекает `natives/<os>-<arch>/<файл>` из jar во временный каталог и загружает его через `SymbolLookup.libraryLookup`. Путь можно задать явно: `-Dberesta.library.path=/path/libberesta.so`.
- Дескрипторы вызовов (`MethodHandle`) строятся один раз по `FunctionDescriptor`, строки передаются через `Arena.ofConfined()` и освобождаются сразу после вызова.
- `XmlDocument`, `XPath`, `XmlSchema` реализуют `AutoCloseable`. Если объект забыли закрыть, нативную память освободит `Cleaner`.
- Узел хранит ссылку на свой документ. После `close()` обращение к узлу даёт `IllegalStateException`, а не падение JVM.
- Методы узла разнесены по интерфейсам (`NodeContent`, `NodeNavigation`, `NodeChildren`, `NodeEditing`, `NodeStructure`, `ElementAttributes`), проверка по схеме — в `SchemaValidation`: можно принимать ровно ту часть API, которая нужна.
- Горячие вызовы обхода (навигация, тип узла, ребёнок по индексу, узлы результата XPath) идут через `invokeExact` с точным типом, остальные — через общий `invokeWithArguments`. JIT встраивает `invokeExact` почти как прямой вызов функции C, поэтому обход дерева из Java стал в 1,4–1,7 раза быстрее.

Самопроверка без Maven и JUnit (нужен только JDK 22+): `make JAVA=1 java-test`.

Как это устроено:
- Функции объявлены через `[DllImport]`; входные строки передаются как `UnmanagedType.LPUTF8Str`, выходные `char*` читаются и сразу освобождаются.

## Python (ctypes)

Пакет `bindings/python/beresta` (Python 3.8+). Он использует только стандартный модуль `ctypes`: ничего не нужно устанавливать и ничего не компилируется на машине пользователя.

```python
import beresta
from beresta import BerestaError, ParseFlags, Schema, WriteFlags, XPath

with beresta.parse("<shop><item code='A1'>Чай</item></shop>") as document:
    item = document.root.first_child
    print(item.get_attribute("code"), item.text)                      # A1 Чай
    print(XPath("//item[@code = $c]", variables={"c": "A1"}).string(document))
    print([child.name for child in document.root])                    # ['item']

with beresta.new_document("order") as order:
    item = order.root.append_element("item")
    item.set_attribute("qty", "2")
    item.append_text("Мёд & орехи")
    order.save("order.xml", WriteFlags.PRETTY, encoding="windows-1251")

try:
    schema = Schema.from_file("order.xsd")
    with beresta.parse_file("order.xml", ParseFlags.TRACK_LOCATIONS) as document:
        for problem in schema.validate(document):                     # готовое дерево
            print(problem.line, problem.message)
        prices = XPath("//item/@price").select_values(document)      # строки без объектов-узлов
    export = schema.validate_file("export.xml")                       # поток без дерева, хоть гигабайты
except BerestaError as error:
    print(error.name, error.message)
```

Подготовка пакета:

```bash
make PYTHON=1
```
```bash
python -m pip wheel bindings/python -w dist
```

Как это устроено:
- Для **каждой** функции заданы `restype` и `argtypes`. Без них ctypes обрезал бы 64-битные указатели до `int`.
- Возвращаемые `char*` объявлены как `c_void_p`, а не `c_char_p`: так указатель не теряется, и строку можно освободить.
- Документ работает как контекстный менеджер (`with`). Если его не закрыли, память освободит `weakref.finalize`.
- Узлы — обычные объекты Python: `len(node)`, `node[i]`, `for child in node`, свойства `text`, `name`, `parent`.
- Обёртка запоминает тип узла и классы обёрток, поэтому на шаг обхода приходится меньше вызовов ctypes, и пошаговый обход стал в 1,6 раза быстрее. Но быстрее всего — не ходить по дереву из Python вовсе: `select_values` собирает строки внутри ядра.
- Библиотека ищется в `BERESTA_LIBRARY`, затем в `beresta/_native/<os>-<arch>/`, затем в системе.

Самопроверка на стандартном `unittest`: `make PYTHON=1 python-test`. Makefile запускает `python` на Windows и `python3` на Linux и macOS; другой интерпретатор задаётся так: `make PYTHON_EXE=/path/python3.12 python-test`.

## Node.js (Node-API)

Пакет `bindings/node` (Node.js 18+, в Node.js 24+ работает `using`). Вызовы идут через собственный аддон на Node-API, а не через `ffi-napi` или node-gyp: объявления стабильного ABI Node-API написаны вручную, а нужные функции аддон находит в процессе Node при загрузке. Поэтому для установки не нужны ни заголовки Node, ни компилятор, ни npm-зависимости — готовый `beresta.node` (около 1–2 МБ, ядро уже внутри) кладёт в пакет сама сборка. Типы TypeScript входят в пакет (`lib/index.d.ts`).

order.root.appendElement('item').setAttribute('qty', 2).appendText('Мёд & орехи');
console.log(order.toXml(beresta.WriteFlags.PRETTY));
order.save('order.xml', { encoding: 'windows-1251' });

using schema = beresta.Schema.fromFile('order.xsd');
for (const problem of schema.validate(order))
    console.log(problem.line, problem.message);
const exported = schema.validateFile('export.xml');                         // поток без дерева

catch (error) { console.log(error.code, error.message); }                   // PARSE_ERROR строка 1, ...
```

```bash
make NODE=1 node-test
```
```bash
make NODE=1 node-package
```

Как это устроено:
- Аддон (`addon/`, C++17) — 31 переходник по сигнатурам для 68 функций Си-интерфейса (паттерны Adapter и Command). Он сам превращает коды ошибок в исключения `BerestaError` с кодом (`PARSE_ERROR`) и текстом на текущем языке.
- Дескрипторы — `BigInt`: адрес не обязан помещаться в 53 бита числа, а одинаковые адреса равны по `===`. Две обёртки одного узла сравниваются через `node.isSameNode(other)`.
- Разбор `Buffer` и `Uint8Array` идёт без копирования байтов; строка кодируется в UTF-8.
- `XmlDocument`, `XPath` и `Schema` закрываются через `close()` или `using` (`Symbol.dispose`). Если забыть, память освободит `FinalizationRegistry`.
- Данные аддона хранятся отдельно для каждого окружения (`napi_set_instance_data`), поэтому пакет работает и в `worker_threads`.
- Аддон ищется в `BERESTA_NODE_ADDON`, затем в `native/<os>-<arch>/beresta.node`.
- Пример на TypeScript запускается без компилятора (Node.js 23.6+): `node bindings/node/examples/demo.mts`.
- Пакет из npm содержит аддоны всех платформ (см. [Готовые пакеты и релизы](#готовые-пакеты-и-релизы)); для браузера есть `beresta-wasm` с тем же API.

## WebAssembly (браузер и Workers)

Пакет `bindings/wasm` (`beresta-wasm`): ядро, собранное Emscripten, и **тот же JS-слой, что у Node.js** — классы, методы и ошибки совпадают, только API становится доступен после `await init()`.

for (const problem of schema.validate(order))
    console.log(problem.message);                 // /order/item[3]: атрибут "price": значение "-5" меньше минимума 0
const problems = schema.validateBytes(fileBytes); // поток без дерева: Uint8Array из <input type="file">
console.log(new beresta.XPath('sum(//@price)').number(order));
order.close();
schema.close();
```

```bash

```

Готовая страница-пример — `bindings/wasm/examples/browser.html`: XML, XSD и XPath, которые проверяются прямо в браузере. Откройте её через любой статический сервер (`python -m http.server --directory bindings/wasm`, затем `http://localhost:8000/examples/browser.html`).

Как это устроено:
- Ядро компилируется `em++` с `-fwasm-exceptions` (исключения C++ средствами самого Wasm) и экспортирует те же функции Си-интерфейса, что и динамическая библиотека (`bindings/wasm/exports.json`).
- `lib/native_wasm.js` — бэкенд для общего JS-слоя (паттерн Adapter): та же таблица функций, что у аддона Node.js, а 31 сигнатура описана данными (`wasm_signatures.js`), и один общий вызов кладёт строки и байты в память Wasm, разбирает результат и превращает ошибки в `BerestaError`.
- Слой написан в CommonJS, а браузеру нужен ES-модуль, поэтому `tools/bundle.mjs` — собственный сборщик без зависимостей: он обходит `require`, подменяет загрузчик аддона на бэкенд Wasm и пишет один файл `dist/beresta.mjs`. Классы не дублируются: правка в `bindings/node/lib` сразу попадает и в браузерный пакет.
- Модуль весит около 650 КБ (около 250 КБ в gzip). Разбор — примерно две трети скорости нативного аддона, XPath — не медленнее.
- В Cloudflare Workers модуль передаётся через `init({ instantiateWasm })` (пример — в `bindings/wasm/README.md`); CI проверяет браузер и Node.js, а Workers — нет.

## Ограничения

Осознанные ограничения (KISS / YAGNI):

- **XML Schema** — подмножество XSD 1.0:
  - при загрузке схемы не проверяются корректность ограничения модели содержимого при `restriction` (cos-particle-restrict) и однозначность модели (UPA): неоднозначная модель принимается и проверяется точно, без выбора первой ветки;
  - из XSD 1.1 есть только `xs:override`; `xs:assert`, `xs:alternative` и открытые модели не поддерживаются;
  - значения по умолчанию из схемы в DOM не добавляются;
  - у `duration` нет порядка для фасетов-границ;
  - категории Unicode в `pattern` (`\p{L}` и т.п.) покрывают основные письменности (латиница, кириллица, греческий, иврит, арабский, CJK), а не всю таблицу Unicode.
- **XPath:** поддерживается XPath 1.0 полностью; XPath 2.0/3.1 (система типов XSD, последовательности, FLWOR) — отдельный язык, и в «Берёсту» он не входит. Его нет и в Xerces, Xalan, libxml2 и System.Xml.
- **XInclude:** атрибут `xml:base` у включённого содержимого не добавляется; XPointer — только `element()` и ID.
- **Кодировки:** восемь перечисленных выше. Остальные нужно перекодировать заранее или добавить своей таблицей.
- **Нет** XSLT, DOM Range, XML 1.1-специфики (`version="1.1"` разбирается по правилам 1.0) и сетевой загрузки.
- **Внешняя сущность с `version="1.1"`** в текстовой декларации отвергается. 5-я редакция XML 1.0 этого прямо не требует; так сделано по случаю W3C `rmt-e2e-38` (errata 2-й редакции: документ XML 1.0 не может включать сущность XML 1.1).
- **Инструкции обработки внутри DTD** передаются SAX-обработчику (`dtdProcessingInstruction`, по умолчанию — обычный `processingInstruction`), но узлами DOM не становятся: у `DocumentType` нет детей. PI внутреннего подмножества сохраняются в тексте `getInternalSubset()` и при сериализации.
- **Экстремальная глубина.** Рекурсии нет нигде, поэтому стек не переполнится. Но некоторые результаты сами растут быстрее глубины: суммарная длина отступов красивого вывода и ключи порядка документа в XPath пропорциональны глубине на каждый узел (путь в сообщении валидатора XSD тоже, но он строится только при ошибке). На деревьях в десятки тысяч уровней эти операции заметно медленнее. Парсер по умолчанию ограничивает глубину значением `maxDepth` = 1024.
- **Си-интерфейс и обёртки** покрывают DOM, XPath и XML Schema, включая потоковую проверку без дерева. Собственный SAX-обработчик, `TreeWalker`, свой `ResourceResolver` и тонкие настройки `ParserOptions` (лимиты, принудительная кодировка) доступны только из C++. Из обёрток лимит глубины всегда 1024: документ глубже даёт `LIMIT_EXCEEDED`, а не переполнение стека. DTD-проверка и XInclude в других языках включаются флагами разбора. Узлы в обёртках живут внутри своего документа, но их можно и копировать (`copyTo` / `CopyTo` / `copy_to`), и переносить без копирования (`moveTo` / `MoveTo` / `move_to`), в том числе между документами. Создать узел без документа, как в C++, из других языков нельзя, а корневой элемент документа не переносится — только копируется. Обход дерева по шагам из обёрток в десятки и сотни раз медленнее, чем из C++: каждый шаг — вызов через границу языка; для массовой обработки используйте XPath (`selectValues`) или SAX в C++.
- **Узел после удаления.** После `remove()` обёртка удалённого узла и обёртки его потомков недействительны, обращаться к ним нельзя. Документ проверяет только собственное закрытие.
- **32-битные платформы** поддерживаются ядром, но обёртки проверялись на 64-битных.
- **WebAssembly:** файловой системы нет, поэтому `parseFile`, `save`, `Schema.fromFile`, `validateFile` и загрузка внешних DTD, сущностей и XInclude из файлов недоступны: файловые функции сразу дают `IO_ERROR` с объяснением. Разбирайте и проверяйте строки и байты, выводите в строку.
- **Потоковая проверка по XSD** (`SaxParser` со схемой) проверяет ключи `xs:key`/`xs:unique`/`xs:keyref` только с селекторами и полями из грамматики XSD; выражения сверх неё (их принимает проверка по дереву) потоково не вычисляются, и об этом приходит сообщение. Ошибки схемы сообщаются после конца документа (номера соседей в путях известны лишь тогда). Файл (`parseFile`, `validateFile`) отображается в память: собственная память процесса остаётся O(глубины), а страницы файла ОС подгружает и выгружает сама. Строку, буфер и `std::istream` парсер получает целиком — без дерева, но не потоком байтов.
- **Поиск атрибута по имени** (`getAttribute`, `hasAttribute`) — перебор, как в libxml2, Xerces и pugixml. При разборе повторы ищутся хеш-таблицей, поэтому тег с 50 000 атрибутов разбирается за линейное время; читать много атрибутов лучше через `getAttributes()` или XPath.

│   ├── node/                     пакет npm: addon/ (Node-API, C++), lib/ (JS + index.d.ts), test/, examples/

Ядро и Си-интерфейс — около **19,8 тысячи строк кода** без комментариев и пустых строк (300 файлов реализации, 97 заголовков; вместе с двуязычными комментариями — около 32 тысяч строк). Обёртки — ещё около 6,8 тысячи строк кода на Java, C#, Python, JavaScript и C++ (аддон Node.js).

### Устройство парсера

```
байты ──► encoding::decodeDocument ──► UTF-8 ──► ParseSession ──► [ValidatingHandler] ──► ContentHandler
              (BOM, декларация,                (итеративный цикл,   (XSD по ходу       ├── DomBuilder ──► Document ──► XInclude
               проверка символов)               стек сущностей,       разбора, если      └── ваш SAX-обработчик
                                                пространства имён,    задана схема)
                                                DTD + валидатор)
```

### Устройство обёрток

```
Java (FFM API) ──┐
C# (P/Invoke) ───┤
Python (ctypes) ─┼──► beresta_c.h ──► барьер исключений ──► ядро C++ (DOM, XPath, XSD, ...)
Node.js (аддон   ┤    (extern "C",     (код + сообщение
  Node-API) ─────┤     void*-дескрипторы) в thread_local)
WebAssembly ─────┤
C, Go, Rust ─────┘
```

Обёртка узла — это нативный дескриптор плюс ссылка на документ-владелец: пока жива обёртка, документ не соберёт сборщик мусора, а после закрытия документа обращение к узлу даёт исключение вместо падения процесса. Каждый документ хранит реестр своих обёрток со слабыми ссылками (паттерн Identity Map): у одного узла одна обёртка. Благодаря реестру перенос (`moveTo`) меняет владельца у всех уже выданных обёрток поддерева сразу.

## Тесты

```bash
make test
```

**159 тестов C++ в 53 наборах:**
- ядро: копирование, иерархия, элементы, навигация, пространства имён, сериализация, деревья глубиной 100 000 уровней;
- парсер: форматы, содержимое, ошибки, лимиты, SAX (в том числе PI из DTD), кодировки, защита от атак на сложность (повторы атрибутов за порогом перебора, хеш с секретным ключом, линейный рост времени разбора от 50 000 до 200 000 атрибутов), отображение файлов в память (кириллические имена, пустой файл, CRLF и windows-1251);
- DTD: сущности, проверка валидности, внешние ресурсы;
- сериализатор, обход дерева, XPath (пути, оси, функции, ось `namespace`, имена), XSD (типы, схемы, расширенные возможности, `xs:key`/`xs:unique`/`xs:keyref`, пути в сообщениях об ошибках, правила пробелов, группы замены, `xsi:type` с `block`/`final`/`abstract`, `xs:redefine`/`xs:override`; потоковая проверка: SAX, DOM и готовое дерево дают одинаковые ошибки, потоковые ключи, глубокий документ), рекурсивная схема глубиной 10 000 уровней с `xs:unique` во всех трёх режимах), модель содержимого (пошаговый курсор против общего алгоритма на тысячах случайных моделей), XInclude;
- Си-интерфейс: коды ошибок, построение и изменение дерева, перенос узлов между документами (с освобождением исходного документа и откатом отвергнутого переноса), XPath, XML Schema, потоковая проверка (совпадает с проверкой дерева, файлы, ошибки); нагрузка, как у обёрток: 20 потоков на общих схеме, XPath и документе (ошибки у каждого потока свои), 50 000 переносов между документами с проверкой каждого ранее выданного дескриптора;
- языки сообщений: полнота каталогов (у каждого сообщения есть перевод с теми же метками `{N}`), смена языка во время работы, подстановка аргументов;
- регрессии: расхождения с набором W3C (синтаксис, сущности, валидность, кодировки) и находки фаззинга.

Соответствие стандарту и устойчивость к враждебному вводу проверяются отдельно:

```bash
cd tests/conformance && make fetch && make run      # W3C XML Conformance Test Suite -> conformance_report.md
cd tests/fuzz && make -j && make corpus && make -j3 fuzz FUZZ_TIME=600 FUZZ_JOBS=3   # libFuzzer, только Clang
```

Тесты проходят в обычной сборке, под AddressSanitizer + UBSan + LeakSanitizer с `-D_GLIBCXX_ASSERTIONS` и под ThreadSanitizer.

Самопроверки обёрток работают без тестовых фреймворков (JUnit, xUnit и pytest не нужны):

```bash
make JAVA=1 CSHARP=1 PYTHON=1 NODE=1 bindings-test
```

Проверяются разбор, навигация, построение, копирование и перенос между документами (в том числе «перенести из A в B, закрыть A, пользоваться узлом в B»), ошибки, запись в другой кодировке, XPath, XML Schema, потоковая проверка (совпадает с деревом, файлы с кириллическими именами), нагрузка (50 000 переносов с сохранением реестра обёрток, 8 потоков на общих схеме и XPath) и языки сообщений: Java — 17 проверок, C# — 16, Python — 21, Node.js — 19 (встроенный `node --test`), WebAssembly — 6 (`make wasm-test`). В CMake всё это (и тесты C++) запускает `ctest`, если включены `BERESTA_BUILD_TESTS` и флаги обёрток.

Как добавить набор C++:
1. Функции тестов в `tests/src/<модуль>/..._tests.cpp`.
2. `registerXxxTests(test::TestRunner&)` в том же файле и объявление в `tests/include/suites/test_suites.hpp`.
3. Строка в таблице `SUITES` в `tests/src/main.cpp`.

Проверки: `TEST_ASSERT(условие)`, `TEST_ASSERT_EQ(строка, "ожидание")`, `TEST_ASSERT_THROWS(инструкция, ТипИсключения)`.

## Расширение библиотеки

«Берёста» не использует сторонних библиотек — ни в ядре, ни в обёртках, ни в тестах. Расширяя её, сохраняйте это свойство: алгоритм, таблицу или разборщик лучше написать самостоятельно.

**Новый тип узла:**
1. Значение в `NodeType` (и в `beresta_node_kind` Си-интерфейса).
2. Наследник `CharacterNode` или `ContainerNode` с `getType`, `clone`, `serialize`, `isEqualNode` (и `validateChild` для контейнера).
3. Обработка в `Document::validateChild`, `DomBuilder`, `showMaskFor` и, при необходимости, в осях XPath.

**Новая кодировка:** таблица из 128 кодов в `src/encoding/tables/`, объявление в `single_byte_tables.hpp`, экземпляр и псевдонимы в `charset_registry.cpp`.

**Новая функция XPath:** реализация с сигнатурой `XPathValue f(const FunctionCall&)` и строка в таблице `FUNCTIONS` (`xpath_function_table.cpp`).

**Свой загрузчик ресурсов:** наследник `ResourceResolver`.

**Новое сообщение об ошибке:** константа в `include/i18n/message.hpp` и текст в каждом каталоге `src/i18n/catalogs/` с одинаковыми метками `{N}` (это проверяет тест «полнота каталогов»). В коде — `i18n::format(i18n::Message::ИМЯ, {аргументы})` вместо строкового литерала.

**Новый язык сообщений:** см. [Как добавить язык](#как-добавить-язык).

**Комментарии** пишутся на двух языках: сначала русский текст, затем его английский перевод в том же комментарии (`// русский` и следующей строкой `// English`, или `// русский / English` для короткого хвостового комментария).

**Новая функция Си-интерфейса:**
1. Объявление с `BERESTA_API` в `include/capi/beresta_c.h` (типы — только C: `void*`, `int`, `int64_t`, `uint32_t`, `double`, `const char*`).
2. Реализация в `src/capi/<группа>/` в обрамлении `BERESTA_CAPI_TRY` … `BERESTA_CAPI_CATCH(...)`: ни одно исключение не должно выйти наружу.
3. Строка-сигнатура в каждой обёртке: `_signatures.py` (Python), `*Functions.java` (Java), `NativeMethods.*.cs` (C#), строка в `bindings/node/addon/src/module/binding_table.cpp` (Node.js; переходник для новой сигнатуры — в `adapters/`), строка в `BINDINGS` в `bindings/wasm/lib/wasm_signatures.js` и имя в `bindings/wasm/exports.json` (WebAssembly; новая сигнатура описывается там же данными). Затем метод в объектном API обёртки.
